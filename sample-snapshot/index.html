01How it was made

How this sample differs from a Snapshot.

We want to be plain about this.

A paid Security Snapshot is one day of hands-on testing of one web app, API or LLM feature, within the scope of a signed authorization letter. This sample went further than that. Because we owned both targets, it was grey-box testing with registered test accounts and active exploitation of the demo apps, including authentication bypass, privilege escalation through registration, and storing test payloads. That depth, against applications built to be insecure, is why it produced 13 findings with saved requests and responses. A standard Snapshot is narrower, and its exact depth is set by the client’s scope and authorization letter.

  • A Snapshot delivers a written report with a threat model and every finding ranked by severity, plus a recommended next step with a fixed quote.
  • Broader and deeper testing like the work in this sample is part of a full LLM Security Review or AppSec Assessment, and always starts with a signed scope and testing authorization.
  • The report structure is the same: a threat model first, then findings with severity ratings, evidence and remediation guidance.

Method used in the sample, as stated in the report: grey-box testing following the OWASP Web Security Testing Guide, the OWASP API Security Top 10 (2023) and the OWASP Top 10 for LLM Applications (2025). Severity follows CVSS v3.1 base score bands. The chatbot is a deterministic stub that imitates an unsafe language-model integration, with no external AI service; its results illustrate design flaws, not the behaviour of any particular AI model.

02What is in the report

Seven parts, threat model first.

One detail we like: where the saved evidence did not fully support an initial rating, the report lowers it and says why, in a rating note on the finding.

  1. Executive summary in plain language, with top priorities and what went well
  2. Scope and approach, including what was out of scope, how the sample’s depth compares with a standard Snapshot, and how severity is rated
  3. Threat model for the two demo apps: assets, likely attackers, and entry points and trust boundaries, each mapped to the findings
  4. Findings summary table
  5. Detailed web application findings (OWASP Juice Shop): description, business impact, evidence, steps to reproduce, remediation guidance, references and a rating note
  6. LLM and RAG assessment of the test chatbot, with a coverage table mapped to the OWASP Top 10 for LLM Applications and AI-specific recommendations
  7. Strategic recommendations, test log, tools and data handling

03Featured findings

Six findings, in the report’s own words.

Titles, severities and wording below are taken from the sample report. Secrets in the report are masked, and the API key in the chatbot findings is a fake value planted for the demo.

WEB-01Juice Shop

SQL injection in login allows authentication bypass as administrator

CriticalCVSS v3.1 9.1

What we foundThe login endpoint builds its database query from the email value without parameterization, and a crafted value logs the caller in as the administrator. No valid credentials are needed.

Remediation guidanceUse parameterized queries or the ORM's query builder for all database access, add automated tests with SQL metacharacters, and alert on anomalous logins.

WEB-06Juice Shop

Mass assignment lets anyone register as administrator

CriticalCVSS v3.1 9.1

What we foundThe registration endpoint copies every field in the request into the new account, including role, so adding "role":"admin" to a normal sign-up creates an administrator account.

Remediation guidanceAccept only an explicit allowlist of fields at registration, set the role on the server, and use separate input models from database models.

WEB-04Juice Shop

Customers can read other users' shopping baskets (IDOR)

MediumCVSS v3.1 4.3

What we foundThe basket endpoint returns any basket whose ID is requested, without checking that it belongs to the logged-in user. Only read access was tested.

Remediation guidanceLook up objects through the authenticated user rather than the ID in the URL alone, and add automated tests that user A cannot read user B's objects.

CHAT-01test chatbot

Direct prompt injection reveals system prompt and internal documents

HighCVSS v3.1 7.5

What we foundA single message asking the assistant to ignore previous instructions made it print the full system prompt and every retrieved document, including an internal runbook. Rules written in a system prompt are not a security control.

Remediation guidanceTreat the system prompt as public and never rely on it to protect data or enforce permissions.

CHAT-02test chatbot

Indirect prompt injection through a retrieved document

MediumCVSS v3.1 4.6

What we foundA document simulating a customer-uploaded review contains hidden instructions. When a different user asks an ordinary question, the document is retrieved and the assistant follows its instructions instead of answering. The user's own message contained no injection.

Remediation guidanceTreat retrieved and uploaded content as untrusted data, restrict who can add documents, and limit what the assistant may do after reading untrusted content.

CHAT-03test chatbot

Sensitive data leakage from the knowledge base

HighCVSS v3.1 7.5

What we foundNo injection is needed. A plain question returns the (fake) production API key, and the retrieval endpoint returns raw documents with no access control, redaction or output filtering.

Remediation guidanceKeep secrets out of knowledge bases, and filter documents by the requesting user's permissions before they reach the model.
